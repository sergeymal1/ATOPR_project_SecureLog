# Сценарій атаки

Запуск: `dotnet run -c Release --project src/SecureLog.App -- attack`. Код: `src/SecureLog.App/Attack.cs`, `src/SecureLog.Security/WeakCipher.cs`, демонстрація — `AttackDemo` у `Program.cs`.

## 1. ГА відновлює ключ слабкого шифру

**Ціль.** Навмисно слабкий шифр: XOR відкритого тексту з ключем 7 байтів, що повторюється. У форматі LOG3 він не використовується; AES не атакується.

**Що знає нападник.** Шифротекст (перші 16384 байти журналу сесії, зашифровані випадковим ключем) і окремий навчальний журнал `train.csv` того самого типу. Відкритого тексту сесії та ключа він не має.

**Ідея.** Байти журналу розподілені дуже нерівномірно: багато нулів у старших байтах полів, малі значення category і severity. Правильний ключ повертає цей розподіл, хибний — розмиває його.

**Хромосома** — 7 байтів ключа. **Пристосованість** — середній логарифм імовірності розшифрованих байтів за частотами навчального журналу (зі згладжуванням Лапласа). **Оператори:** турнірна селекція з 3, рівномірний кросовер по байтах, мутація одного випадкового байта з імовірністю 0.6, елітизм 2. Популяція 100, 300 поколінь, 29500 обчислень пристосованості.

**Результат прогону 13.11.2026:**

```
справжній ключ:   EA47B3EF517244
відновлений ключ: EA47B3EF517244 — збіглося 7/7 байтів за 29500 обчислень пристосованості
```

Ключ щоразу випадковий; тест `Attack_GaRecoversWeakCipherKey` перевіряє те саме на фіксованому ключі.

**Чому атака працює.** Пристосованість розкладається в суму за позиціями ключа, тому кожен правильний байт підвищує її незалежно від інших, а кросовер збирає правильні байти з різних особин.

**Межа атаки.** Довжина ключа взаємно проста з розміром запису (16 байтів), тому кожен байт ключа зустрічає всі поля запису. Якщо взяти ключ у 8 байтів, кожен його байт припадатиме лише на два поля. Байт, що шифрує молодші байти `timestamp_ms` і `metric_value`, тоді не відновлюється: ці байти майже рівномірні, і за частотами всі варіанти ключа виглядають однаково. Перша версія тесту з ключем у 8 байтів саме на цьому й упала.

**Чому так не зламати AES-256-CTR.** Гама AES не повторюється з періодом довжини ключа: кожен блок шифрується власним значенням лічильника. Шифротекст статистично не відрізняється від випадкових байтів (таблиця 4 у `docs/results/tables.md`: Гаффман його не стискає), тож у пристосованості немає сигналу, за яким ГА міг би рухатись.

## 2. Перевірка цілісності

Нападник, що має доступ до вузла, змінює один біт шифротексту репліки. Відновлювач рахує HMAC-SHA256 над заголовком і шифротекстом, порівнює його за сталий час і відхиляє репліку з кодом `E_HMAC`, не розшифровуючи її:

```
змінено 1 біт шифротексту: відхилено реплік 1, прийнято подій 0
```

Тест `C10_AnyModifiedByteIsRejected` повторює це для кожного байта репліки, включно із заголовком і самим HMAC. Відхилена копія не зупиняє відновлення: запис береться з копії на іншому вузлі (`C11_BadInputsAreRejectedWithoutCrash`).

## Чого немає

Аналіз метаданих (визначення типу активності за розмірами й частотою реплік без розшифрування) — просунутий рівень, не реалізований.
